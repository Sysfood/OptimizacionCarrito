## Entidades del modelo de dominio

| Entidad | Operación en esta historia | Atributos usados | Asociaciones y multiplicidades |
|---------|----------------------------|------------------|---------------------------------|
| Pedido | crea, lee y actualiza el pedido mientras se arma | `estado` (En edición), `/total` | Cliente 1 – 0..* Pedido; Jornada 1 – 0..* Pedido; Pedido 1 – 1..* DetallePedido |
| DetallePedido | crea, modifica y elimina | `cantidad`, `precioUnitario` | Pedido 1 – 1..* DetallePedido; Producto 1 – 0..* DetallePedido |
| Producto | lee el nombre y el precio vigente | `nombre`, `precio` | Producto 1 – 0..* DetallePedido |
| Existencia | lee las unidades vendibles para validar cantidades y buscar alternativas | `/unidadesVendibles` (`unidadesAsignadas − unidadesReservadas − unidadesConsumidas`) | Jornada 1 – 0..* Existencia; Producto 1 – 0..* Existencia |
| Cliente | usa un cliente de demostración fijo, porque no hay autenticación real | `nombre`, `contacto` | Cliente 1 – 0..* Pedido |
| Jornada | asocia el pedido a la jornada vigente | `fecha`, `horaApertura`, `horaCierre`, `recepcionDigital` | Carrito 1 – 0..* Jornada; Jornada 1 – 0..* Pedido |

- El **subtotal** de cada detalle se calcula como `cantidad × precioUnitario` y el **total** como la suma de los subtotales; no se almacenan por separado, tal como define el modelo (`/total`).
- `precioUnitario` guarda el precio vigente al agregar el producto. Si el precio cambia antes del pago, la revalidación compara ese valor con el precio actual y exige aceptación del nuevo total.
- El pedido **no asigna `código` ni `fechaHoraConfirmación`** en esta historia; eso ocurre al confirmar el pago (HU-03).

## Flujo de interacción

1. El estudiante agrega un producto con una cantidad desde el catálogo.
2. El sistema compara la cantidad con las unidades vendibles del producto en la jornada vigente.
3. Si la cantidad supera lo vendible, la rechaza, informa la cantidad máxima que puede solicitar y muestra otros productos con unidades vendibles como alternativas, sin reemplazar el producto sin decisión del estudiante.
4. Si la cantidad es válida, el sistema registra el detalle con el precio vigente y calcula el subtotal y el total.
5. El estudiante puede modificar la cantidad o eliminar el producto; el sistema recalcula subtotal y total con la selección vigente.
6. Al pulsar **«Continuar al pago»**, el sistema revalida el precio y la disponibilidad de todos los detalles.
7. Si el precio o la disponibilidad cambiaron, el sistema identifica el producto o valor afectado, muestra el nuevo total y no permite continuar hasta que el estudiante acepte el nuevo total.
8. Si todo coincide, o el estudiante acepta el nuevo total, el pedido queda listo para pagar. La pantalla de pago pertenece a HU-03.

**Variantes:**
- Producto agotado: se informa y se muestran alternativas disponibles, si existen; ninguna se incorpora sin decisión del estudiante.
- Cantidad superior a la vendible: se rechaza y se informa el máximo disponible.
- Precio o disponibilidad cambiados antes del pago: se informa qué cambió y se exige aceptación del nuevo total.
- Cantidad mínima: 1. Para quitar un producto se usa la acción **Eliminar**, no una cantidad 0.
- Para demostrar el cambio de precio o de disponibilidad se usará un control de demostración, similar al de HU-01.

```gherkin
Característica: Construcción y revisión de un pedido

    Cuando el estudiante intenta continuar con esa cantidad

    Y se informa la cantidad máxima que puede solicitar
    Y se muestran alternativas disponibles, si existen, sin reemplazar el producto sin su decisión

    Dado que el estudiante tiene un pedido preparado
    Y el precio o la disponibilidad de uno de sus productos cambió
    Cuando se revalida el pedido antes del pago
    Entonces se informa qué producto o valor cambió
    Y no se inicia el pago hasta que el estudiante acepta el nuevo total
```

## Decisiones tomadas en la validación

- **AC-02 y su trazabilidad:** la historia cita AC-02 y RP-03, aunque la tabla de `02-rediseno-to-be.md` asocia AC-02 solo a HU-01 y HU-08. Se mantiene que HU-02 cubre la validación de disponibilidad y las alternativas; la tabla no se modifica sin una nueva autorización.
- **Estado «En edición»:** se agrega a EST-01 y a `diagramas/est-01.puml` como estado inicial del Pedido. HU-02 crea el pedido allí y HU-03 lo lleva a «Pendiente de pago». Aprobado por el estudiante el 2026-11-18.
- **Cliente de demostración:** se usa un cliente fijo creado por los datos de ejemplo, ya que no hay autenticación real.
- **Fin de HU-02:** el flujo termina cuando el pedido queda listo para pagar; no se implementa la pasarela ni el pago.
- **Cantidad mínima 1** y acción «Eliminar» para quitar un producto.
- **Alternativas:** se ofrecen otros productos con unidades vendibles de la misma jornada, sin reemplazo automático.
- **Control de demostración:** permitirá cambiar un precio o consumir unidades para reproducir el último escenario.

## Supuestos

- **DSS-01:** su encabezado dice «Caso de uso: CU-03», pero se usa el mapeo ya confirmado en `.cin324/proyecto.md`: DSS-01 corresponde a CU-02. No se modifica el documento.
- **Jornada del pedido:** se usa la jornada más reciente con existencias cargadas, la misma que muestra el catálogo de HU-01.
- **Precio en CLP:** se mantiene el precio entero en pesos chilenos definido en HU-01.
- **RP-17:** la meta de ≤6 acciones se usa como criterio de diseño, pero no se instrumenta ni se mide en esta historia.
- **Sin categorías de productos:** las alternativas son cualquier otro producto disponible, porque el modelo no tiene categorías.
